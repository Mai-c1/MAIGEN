# MAIGEN AI 提示词编写规范与最佳实践

本文档旨在指导管理员如何编写高效、准确且安全的 AI 提示词，以驱动 MAIGEN 系统的算法数据生成模块。

## 1. 核心机制理解 (Under the Hood)

了解底层逻辑是写好 Prompt 的前提：

### 1.1 智能分流 (Smart Parsing)
系统会自动将 AI 的输出拆分为两部分：
- **纯代码 (`_code`)**: 被 ` ``` ` 包裹的内容（如 Python 脚本）。
- **纯文本 (`_text`)**: 代码块之外的所有自然语言（如分析报告）。

> **关键启示**: 在 Step 3 (生成) 中，必须要求 AI **只输出代码块**，或者确保代码块包含完整逻辑。

### 1.2 上下文变量 (Context Variables)
每一步的产出都会自动注册为变量，供后续步骤引用：
- `{step_N_code}`: 第 N 步生成的纯代码（无废话）。
- `{step_N_text}`: 第 N 步生成的分析文本（无代码）。
- `{title}`, `{description}`, `{standardCode}`: 题目基础信息。
- `{timeLimit}`, `{memoryLimit}`, `{testcaseCount}`: 题目限制条件。

### 1.3 实时反馈 (Real-time Feedback)
- **预览**: 系统会截取 AI 分析文本的前 **30 个字符** 推送到前端进度条。
- **截断**: 任务失败时的报错信息会被截断为 **100 个字符**。

> **关键启示**: 让 AI **结论先行**。例如让 Step 1 输出 "【分析结论】本题核心变量为 N..."，这样用户一眼就能看到重点。

### 1.4 自动反馈闭环 (Auto-Feedback Loop)
- 如果 Step 4 (审计) 输出包含 `[FAIL]`，系统会提取审计意见，**强制回滚** 到 Step 3 并让 AI 重写。
- 最大重试次数：3 次。

## 2. 标准 4-Agent 流水线配置 (Templates)

请严格按照以下 4 个角色配置工作流：

### Step 1: 题目分析师 (Modeler)
*   **目标**: 识别题目中的自变量 (N, M) 和拓扑约束。
*   **System Prompt**:
    ```text
    你是数学建模专家。请从题目描述中抽象出决定计算复杂度的核心自变量。
    【输出要求】
    1. 纯文本分析，不要代码。
    2. 第一句话必须是核心结论（如“核心变量是序列长度 N”）。
    ```
*   **User Prompt**:
    ```text
    题目描述：{description}
    标准代码：{standardCode}
    请建立数据生成模型。
    ```

### Step 2: 策略规划师 (Strategist)
*   **目标**: 设计测试用例的分布（极小、边界、随机）。
*   **System Prompt**:
    ```text
    你是全覆盖测试专家。请规划 {testcaseCount} 组测试用例的分布。
    【要求】
    1. 包含梯度分布、边界覆盖和特殊形态。
    2. 第一句话简述规划思路。
    ```
*   **User Prompt**:
    ```text
    数据模型：{step_1_text}
    请输出 {testcaseCount} 个测试点的设计方案。
    ```

### Step 3: 代码生成专家 (Implementer)
*   **目标**: 编写 Python Cyaron 脚本。
*   **System Prompt**:
    ```text
    你是 Python Cyaron 专家。请将策略转化为代码。
    【规范】
    1. 必须使用 `from cyaron import *`
    2. 循环 `for i in range({testcaseCount}):`
    3. 动态计算规模，禁止硬编码 N=1000。
    【输出要求】
    只输出 Python 代码块。
    ```
*   **User Prompt**:
    ```text
    策略方案：{step_2_text}
    请编写 Python 脚本。
    ```

### Step 4: 合规性审计 (Auditor)
*   **目标**: 检查代码安全性与逻辑闭环。
*   **System Prompt**:
    ```text
    你是代码审计员。检查代码是否安全且语法正确。
    【规则】
    - 通过：仅输出 `[PASS]`
    - 失败：输出 `[FAIL]` 并说明原因
    ```
*   **User Prompt**:
    ```text
    待审计代码：{step_3_code}
    请审计。
    ```

## 3. 避坑指南 (Do's and Don'ts)

| 行为 | 示例 | 后果 |
| :--- | :--- | :--- |
| ✅ **引用纯代码** | 使用 `{step_3_code}` | 审计员只看到代码，不受废话干扰，Token 消耗少。 |
| ❌ **引用混合内容** | 使用 `{step_3_result}` | 上下文包含大量废话，可能导致 Token 溢出或 AI 混淆。 |
| ✅ **结论先行** | "核心变量是 N..." | 用户在前端能看到清晰的预览。 |
| ❌ **废话连篇** | "经过仔细阅读..." | 用户在前端只看到 "经过仔细阅读题目描述我发现..."，毫无信息量。 |
| ✅ **明确失败标记** | 规定输出 `[FAIL]` | 触发自动重试，AI 自我修正。 |
| ❌ **模糊失败反馈** | "代码有问题" | 系统无法识别失败，任务直接结束（得到错误代码）。 |
